# Архитектура игры «Корвин: Путь к Амберу»

## Назначение и принципы

Игра — небольшой 3D-платформер с камерой от третьего лица, четырьмя уровнями и уникальными механиками на каждом из них. Приложение написано на Rust и использует **BFGE как графический движок через публичный API**.

Основной принцип: **BFGE отвечает за окно, цикл кадров и отображение 3D-сцены; игра — за правила, состояние мира и поведение объектов**. Движок не должен знать о Корвине, Отражениях, платформах, чекпоинтах или сценариях уровней.

Архитектура намеренно небольшая: один crate игры, BFGE как зависимость, без ECS, отдельного потока симуляции и собственной сложной системы плагинов. Общие механики реализуются один раз и используются всеми уровнями.

## Компоненты и ответственность

| Компонент | Ответственность |
| --- | --- |
| **Application** | Инициализация BFGE и игры, запуск, смена экранов и уровней, завершение приложения. |
| **GameLoop** | Один игровой тик из callback BFGE: учёт прошедшего времени, фиксированные шаги симуляции и вызов синхронизации сцены. **Не содержит отдельного бесконечного цикла.** |
| **Game** | Координация обновления: ввод → намерения персонажа → объекты/физика → события и механика уровня → проверка завершения. Хранит актуальное игровое состояние. |
| **Input** | Снимок состояния клавиатуры/мыши и однократные действия (`jump`, `switch_shadow` и т. п.). Не содержит правил уровня. |
| **Player / Controller** | Положение и состояние Корвина; преобразование команд игрока в движение, прыжки и действия. |
| **Physics** | Простая гравитация, столкновения с активными платформами, определение приземления, перенос движущимися платформами и падение за границы уровня. |
| **World** | Источник истины об игровых объектах: transform, коллайдер, активность и необязательные свойства поведения (движение, разрушение, принадлежность Отражению). |
| **Level** | Сценарий и уникальные правила текущего уровня, контрольные точки, условия победы. Не управляет напрямую графическим API. |
| **Camera** | Расчёт камеры от третьего лица с возможностью смены параметров/режима для отдельных уровней (например, поднятая камера в Лабиринте). |
| **SceneAdapter** | Связь игровых ID с ID объектов/узлов BFGE; создание визуальной сцены и применение изменившихся transform, видимости, цвета, освещения и камеры. |

`Game` и `World` не зависят от конкретных идентификаторов сцены BFGE: игровые объекты идентифицируются собственными `GameObjectId`. `SceneAdapter` хранит соответствие между игровыми ID и BFGE ID.

## Жизненный цикл и поток данных

BFGE уже управляет оконным циклом через `Engine::run()` и вызывает обработчик `frame_started` перед рендерингом. Поэтому отдельный `loop { ... }` в игровом приложении **не нужен**.

```text
Application запускает Engine::run()
             │
             ▼
BFGE: события окна / ввод
             │
             ▼
frame_started → GameLoop.tick(frame_dt, input)
                    │
                    ├─ фиксированные шаги Game.fixed_update(dt)
                    │    ├─ управление персонажем
                    │    ├─ движение объектов и физика
                    │    ├─ триггеры и правила уровня
                    │    └─ состояния, чекпоинты, завершение
                    │
                    └─ SceneAdapter.sync(Game, BFGE Scene API)
                                   │
                                   ▼
                              BFGE: render
```

**GameLoop** накапливает `frame_dt` и вызывает `Game.fixed_update()` с постоянным шагом (ориентир — 1/60 с). Следует ограничивать слишком большой `frame_dt` и число шагов за кадр. Синхронизация визуальной сцены выполняется **один раз на графический кадр**, после шагов симуляции и до рендеринга. При необходимости позже можно добавить интерполяцию визуальных transform между шагами физики.

`update()` **не отправляет кадры в движок**: он изменяет игровое состояние. `SceneAdapter` затем передаёт BFGE только необходимые изменения. BFGE по-прежнему сам формирует и рисует кадр.

**Ввод:** текущий публичный API BFGE не передаёт игре события клавиатуры и мыши; потребуется небольшое расширение движка, чтобы предоставлять `InputState` приложению. Состояние удерживаемых клавиш используется на каждом шаге симуляции, а события одиночного нажатия (`just_pressed`) должны обрабатываться ровно один раз, даже если в графическом кадре выполнено несколько физических шагов.

## Организация уровней

Все уровни используют один `Player`, `World`, `Physics`, `Camera` и `GameLoop`. Различаются **конфигурацией объектов, сценарием и уникальными правилами**.

| Уровень | Уникальная логика |
| --- | --- |
| **Дорога через Отражения** | Переключение двух состояний окружения; одновременно меняются видимость объектов и доступность соответствующих коллайдеров. |
| **Лестница на Колвир** | Разрушающиеся ступени, камнепады и вертикальный маршрут. Универсальное поведение разрушаемых объектов находится в общих системах, а не дублируется в коде уровня. |
| **Тир-на Ног'т** | Платформы с таймерами, движущиеся платформы, этапы приближения рассвета. |
| **Лабиринт Ребмы** | Проверка следования маршруту, сопротивление на участках, завесы и особые настройки движения/камеры. |

Для уровней допустим общий интерфейс (`Level`) или `enum` из четырёх вариантов — выбрать более простой в реализации. Уровень создаёт/настраивает мир, обрабатывает свои события и сообщает о завершении. Поведение типовых объектов (платформа движется, разрушается, исчезает) должно быть переиспользуемым.

Геометрию, расположение объектов, триггеров и чекпоинтов желательно хранить в файлах данных уровней (например, JSON). В коде остаются правила и механики. Не нужно делать универсальный редактор или сложный формат данных на первом этапе.

## Пример структуры проекта

```text
corwin-game/
├── Cargo.toml
├── assets/
│   ├── models/                # Корвин, платформы, окружение
│   └── levels/                # Конфигурации четырёх уровней
└── src/
    ├── main.rs                # Инициализация и запуск
    ├── app/
    │   ├── game.rs            # Координация состояния игры
    │   └── game_loop.rs       # Фиксированный шаг, тик BFGE
    ├── gameplay/
    │   ├── player.rs          # Персонаж и управление
    │   ├── physics.rs         # Простые столкновения и гравитация
    │   └── camera.rs          # Камера от третьего лица
    ├── world/
    │   ├── mod.rs             # World, объекты и состояния
    │   └── components.rs      # Коллайдеры, таймеры, движение
    ├── levels/
    │   ├── mod.rs             # Общий контракт и загрузка уровней
    │   ├── shadows.rs
    │   ├── kolvir.rs
    │   ├── tir_na_noght.rs
    │   └── pattern.rs
    └── engine/
        ├── input.rs           # Адаптация ввода BFGE
        └── scene_adapter.rs   # Синхронизация World ↔ BFGE Scene
```

Структура ориентировочная: не следует создавать пустые модули заранее или разбивать небольшую реализацию на десятки файлов. При росте функциональности допускается выделение модулей для триггеров, чекпоинтов, загрузки данных и состояний приложения.

## Правила для разработки

1. **Сначала изменяется игровое состояние**, затем его визуальное представление в BFGE; графическая сцена не является источником игровой логики.
2. **Уровни не вызывают BFGE напрямую**: они меняют `World` и сообщают игровые события.
3. **Общие механики не копируются между уровнями**. Отличия задаются свойствами объектов и правилами соответствующего уровня.
4. **Ввод, физика и время независимы от FPS**; одиночные действия ввода не должны повторяться в нескольких fixed-step обновлениях.
5. **Добавления в BFGE должны быть минимальными и универсальными**: прежде всего клавиатура и мышь; механики конкретной игры остаются в игровом crate.
6. **Переход между уровнями** создаёт новый игровой мир и заново связывает игровые объекты с узлами сцены; ID старого уровня не используются после смены сцены.

Итоговая граница ответственности: **BFGE предоставляет графическую инфраструктуру; GameLoop управляет временем симуляции; Game и его системы определяют мир; Level задаёт правила; SceneAdapter отражает результат в движке**.
