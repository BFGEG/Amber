# Работа над Amber

Инструкции действуют для всего репозитория. Общение, описания задач и PR, а также проектную документацию пиши по-русски. Имена Rust-типов, функций и модулей — по-английски.

## Где искать ответы

| Вопрос | Источник |
| --- | --- |
| Что представляет собой проект и как его запускать | `README.md` |
| Где находятся исходные описания игры | `docs/README.md` |
| Общие правила игры, механики, камера и объекты | `docs/Corwin_Amber_Game_Design_Document.docx` |
| Маршруты, препятствия и действия игрока по главам | `docs/Corwin_4_Levels_Walkthrough.docx` |
| Какие правила расходятся и какие варианты реализации предложены | `docs/design-choices.md` и связанные issues |
| Что именно нужно сделать сейчас и от каких задач это зависит | Текущий issue в `BFGEG/Amber` |
| Текущая реализация | `src/`, после инициализации Cargo-проекта |
| Версия Rust, состав зависимостей и закреплённая ревизия BFGE | `Cargo.toml` и `Cargo.lock`, после их появления |

Исходные DOCX сохраняй без изменений, если задача прямо не требует их редактирования. Для выбора между вариантами используй описание соответствующего issue. Реализуй один вариант и зафиксируй решение в PR и документации управления или уровня; последующие задачи должны следовать ему. Если выбор существенно меняет соседнюю механику, отрази это в связанном issue.

## Порядок изменений

- Работай в Amber. Другие репозитории не изменяй. Исследование других репозиториев допускается только в явно порученном объёме; подключение BFGE не означает разрешение на его переработку.
- Читай текущий issue и его зависимости до изменения кода. Следуй порядку: запускаемая тестовая сцена, базовое управление и столкновения, затем механики и главы.
- Ограничивай одну задачу и её PR 1000 строками изменений. Если объём растёт, раздели работу на последовательные небольшие задачи. Сгенерированный `Cargo.lock` и исходные бинарные документы учитывай отдельно при оценке объёма кода.
- После появления тестовой сцены каждое изменение должно сохранять возможность запуска и визуальной проверки. Новую механику сначала показывай на небольшом участке.
- Сохраняй пользовательские изменения и файлы IDE. Коммить только файлы текущей задачи.
- Указывай решаемый issue в описании PR через `Resolved #номер`. Для стека явно указывай предыдущий PR и базовую ветку. Не выполняй merge без прямого поручения.

## Стиль Rust

Основной ориентир — [Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html). Применяй общие правила Rust и рекомендации для прикладного кода. Пункты, явно относящиеся к инфраструктуре Chrome, Fuchsia и другим внутренним системам Google, не создают зависимостей или требований к сборке Amber.

- Форматируй код стандартным `rustfmt`; не выравнивай его вручную вопреки форматтеру.
- Предпочитай небольшие функции и модули с понятной ответственностью. Добавляй абстракции и зависимости по потребности текущей задачи.
- Используй принятые Rust-соглашения об именовании, явные импорты и типы, выражающие смысл данных.
- Возвращай ожидаемые ошибки через `Result` и передавай полезный контекст. Используй `Option` для отсутствующих значений. `unwrap` и `expect` допустимы только для обоснованных инвариантов или проверок; поясняй смысл инварианта.
- Предпочитай заимствование лишнему копированию. Делай владение состоянием понятным, особенно для сцен, ресурсов и восстановления участка.
- Документируй неочевидные ограничения и публичные интерфейсы, а не пересказывай очевидные операции. Тестируй наблюдаемое поведение, которое важно для задачи.
- Применяй стабильный Rust. `unsafe` требует конкретного обоснования и документированных условий безопасности.

## Проверка результата

Пока `Cargo.toml` не добавлен, проверяй ссылки документации, сохранность DOCX и состав diff. После инициализации проекта запускай из корня:

```sh
cargo fmt --all -- --check
cargo check --locked
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Для изменений запуска приложения дополнительно выполняй `cargo run --locked`; когда появится игровая сцена — проверяй затронутый участок в ней. Не добавляй формальные тесты только ради покрытия простых правок документации. В PR пиши, что проверено и какие проверки не удалось выполнить.

Изменения зависимостей сопровождай обновлением `Cargo.lock`. BFGE закрепляй полным SHA коммита согласованного релиза, а не плавающей веткой; при обновлении фиксируй релиз и ревизию в README.
